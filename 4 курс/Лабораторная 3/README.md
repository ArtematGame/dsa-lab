# Лабораторная работа №4 «Асинхронная модель исполнения компонента»

Дисциплина «Разработка программных приложений»

## О чём работа

Сервис-**агрегатор поиска авиаперелётов**. Пользователь указывает аэропорт вылета, аэропорт прилёта и дату. Сервис:

1. читает рейсы на эту дату из собственной базы PostgreSQL (1500 рейсов в сутки между 30 аэропортами);
2. запрашивает рейсы у трёх поставщиков (авиаперевозчиков);
3. составляет маршруты: прямые и не более чем с двумя пересадками;
4. возвращает 20 самых дешёвых маршрутов.

Почти всё время обработки запроса сервис не вычисляет, а **ждёт ответов поставщиков**: по профилю около 99 %. Цель работы — показать на замерах и профиле, как от модели исполнения зависит производительность, и перевести сервис на асинхронную модель.

Сервис реализован в **трёх версиях**:

| Версия | Задача | Как устроена | Итог |
|---|---|---|---|
| `sync` | 3.3 | Обработчики через `def` (пул из 40 потоков), `requests`, `time.sleep`, синхронная БД (psycopg). Поставщики опрашиваются **по очереди**. | Поиск укладывается в требование, `/health` под большой нагрузкой — нет |
| `blocking_async` | 4.1 | Тот же код, но обработчики объявлены через `async def`. Блокирующие вызовы останавливают единственный поток цикла событий. | Хуже синхронной, оба требования нарушены |
| `async` | 4.2 | `httpx.AsyncClient`, asyncpg, `asyncio.gather`, `asyncio.timeout`, `asyncio.sleep`. База и поставщики опрашиваются **одновременно**. | Оба требования выполнены |

### Правила предметной области

- На каждого поставщика отводится **2 секунды**, включая повтор.
- Если поставщик вернул ошибку, через **200 мс** запрос повторяется **один раз**.
- Если поставщик не ответил за 2 с или повтор тоже завершился ошибкой, его рейсы в выдачу не попадают, а в ответе перечислены не ответившие поставщики (`unavailable_providers`).
- Если не ответил ни один поставщик и в базе нет рейсов на эту дату, сервис отвечает **HTTP 503 «Поиск временно недоступен»**.
- Маршрут — от 1 до 3 рейсов, все вылетают в дату поиска. Пересадка в аэропорту прилёта предыдущего рейса через **1–6 часов**. Аэропорты в маршруте не повторяются. Стоимость маршрута — сумма цен рейсов.
- Время всех рейсов — UTC, цены — в рублях.

### Параметры поставщиков (таблица 1 методички)

| Поставщик | Средняя задержка | Ошибки 500 | Ответы через 3 с | Рейсов в сутки |
|---|---|---|---|---|
| P1 | 300 мс ± 30 % (210–390 мс) | 5 % | 0 % | 500 |
| P2 | 500 мс ± 30 % (350–650 мс) | 5 % | 0 % | 500 |
| P3 | 800 мс ± 30 % (560–1040 мс) | 5 % | 10 % | 500 |

### Требования к сервису

1. Время ответа на поиск (**p95**) — не более **3 с** при нагрузке **5 запросов в секунду**.
2. Время ответа `GET /health` (**p95**) — не более **100 мс** во всех замерах.

### Что делает каждый файл

**`app/flights.py`** — общие данные.
- `Flight` — описание рейса: перевозчик, номер, откуда, куда, вылет, прилёт, цена.
- `AIRPORTS` — 30 аэропортов, `START_DATE` и `DAYS` — расписание на 120 дней с 19.10.2026.
- `generate(day, source, count)` создаёт рейсы. Генератор случайных чисел получает постоянное начальное значение `"42-источник-дата"`, поэтому для одних и тех же параметров **всегда получаются одни и те же рейсы**. Продолжительность полёта 1–6 часов, цена 1500–20 000 ₽.

**`app/db.py`** — база данных.
- Таблица `flights` с составным ключом «перевозчик + номер + время вылета».
- Индекс `ix_flights_departure` по времени вылета для быстрой выборки за дату.
- `read_sync` — синхронное чтение (psycopg), `read_async` — асинхронное (asyncpg).

**`app/seed.py`** — заполнение базы. Создаёт таблицу и загружает 180 000 рейсов. `ON CONFLICT DO NOTHING` гарантирует, что повторный запуск не создаст дубликатов.

**`app/provider.py`** — заглушка поставщика. Один код запускается тремя контейнерами с разными переменными окружения.
- `GET /flights?date=...` — 500 рейсов за дату, всегда одинаковых для одной даты. Задержка, ошибки 500 и медленные ответы — случайные, по таблице 1.
- Задержка сделана через `await asyncio.sleep`, а не `time.sleep`, чтобы заглушка не обслуживала запросы по одному и не стала узким местом.
- `GET /health` — всегда успешный ответ, используется для проверки готовности.

**`app/routes.py`** — функция `build_routes`. Группирует рейсы по аэропорту вылета, перебирает пути до 3 рейсов, двоичным поиском (`bisect`) отбирает пересадки через 1–6 часов, хранит 20 самых дешёвых вариантов в «куче» (`heapq`). Не обращается ни к сети, ни к базе (задача 3.3, п. 4).

**`app/service.py`** — сервис поиска.
- `lifespan` — один раз при запуске создаёт движок БД и (в версии `async`) `httpx.AsyncClient`.
- `provider_sync` — опрос поставщика через `requests`, общий срок 2 с, пауза `time.sleep(0.2)`.
- `provider_async` — опрос через `httpx` внутри `asyncio.timeout(2.0)`, пауза `asyncio.sleep(0.2)`.
- `finish` — собирает рейсы, вызывает `build_routes`, формирует ответ (или 503).
- `search_sync` — синхронная обработка: база, затем поставщики по очереди.
- В конце файла регистрируются обработчики `/search` и `/health` нужной версии.

**`load.py`** — нагрузочный скрипт на `asyncio` и `httpx.AsyncClient` (задача 3.5). Подробнее — в разделе «Замеры».

**`run_measurements.py`** — запускает все 15 замеров, `py-spy dump` и два профиля, собирает таблицу `results/summary.csv`.

**`estimate.py`** — оценка среднего времени ответа для двух диаграмм и расчёт по закону Литтла (задачи 2.2 и 2.3). Для одновременной схемы нужно среднее **максимума** из времён поставщиков, поэтому оно рассчитано моделированием: 300 000 случайных запросов, начальное значение 42.

## Запуск

### 1. Собрать образ и запустить стенд

```sh
docker compose up -d --build --wait
```

Запускаются 5 контейнеров: `db`, `provider1`, `provider2`, `provider3`, `search`. Флаг `--wait` ждёт, пока все станут готовыми (`healthy`). Сервис поиска стартует только после готовности базы и всех трёх заглушек.

Проверить состояние:

```sh
docker compose ps
```

В столбце `STATUS` у всех должно быть `(healthy)`.

### 2. Заполнить базу (один раз)

```sh
docker compose exec -T search python -m app.seed
```

Будет выведено `Рейсов в базе: 180000`. Повторный запуск ничего не меняет. Данные хранятся в томе `db_data` и сохраняются после `docker compose down`.

### 3. Проверить работу

Открыть в браузере:

- проверка работоспособности: <http://localhost:18040/health> → `{"status":"ok"}`;
- поиск: <http://localhost:18040/search?origin=OVB&destination=SVO&date=2026-10-19>;
- документация API (Swagger): <http://localhost:18040/docs>.

Пример ответа поиска (значения условные, сокращено до одного маршрута):

```json
{
  "routes": [
    {"price": 3120, "flights": [
      {"carrier": "P2", "number": "P20137", "origin": "OVB", "destination": "SVO",
       "departure": "2026-10-19T08:41:00+00:00", "arrival": "2026-10-19T12:05:00+00:00", "price": 3120}
    ]}
  ],
  "unavailable_providers": ["P3"],
  "processing_ms": 1843.512
}
```

- `routes` — до 20 самых дешёвых маршрутов по возрастанию цены;
- `unavailable_providers` — поставщики, которые не ответили за 2 с;
- `processing_ms` — время обработки запроса в миллисекундах.

Допустимые даты: с 2026-10-19 по 2027-02-15. Аэропорты — из списка `AIRPORTS` в `app/flights.py`. Если аэропорт неизвестен или аэропорты совпадают, сервис вернёт ошибку 422.

### 4. Переключить версию сервиса

По умолчанию запускается `sync`. Чтобы запустить другую версию, задайте переменную `SERVICE_VERSION` и пересоздайте только контейнер `search`.

**Windows (PowerShell):**

```powershell
$env:SERVICE_VERSION="async"
docker compose up -d --no-deps --force-recreate --wait search
```

**Windows (командная строка cmd):**

```bat
set SERVICE_VERSION=async
docker compose up -d --no-deps --force-recreate --wait search
```

**macOS / Linux:**

```sh
SERVICE_VERSION=async docker compose up -d --no-deps --force-recreate --wait search
```

Возможные значения: `sync`, `blocking_async`, `async`. Чтобы вернуться к синхронной версии, задайте `sync`.

### 5. Остановить стенд

```sh
docker compose down
```

База при этом сохраняется. Чтобы удалить и её, используйте `docker compose down -v`; после этого нужно снова выполнить шаг 2.

## Замеры

### Нагрузочный скрипт `load.py`

Режимы:

- **замкнутый** (`--mode closed --clients C`) — работает C клиентов; каждый отправляет следующий поиск только после ответа на предыдущий. Показывает, сколько запросов в секунду сервис выдерживает при заданной конкурентности;
- **открытый** (`--mode open --rate 5`) — поиски отправляются в среднем 5 раз в секунду, не дожидаясь ответов. Интервалы случайные, распределены по экспоненциальному закону (`random.expovariate`): так ведут себя реальные пользователи.

Во время нагрузки отдельный клиент каждые 100 мс отправляет `GET /health`.

Параметры замера (по умолчанию): прогрев **10 с** (запросы прогрева не учитываются), измерение **60 с**, тайм-аут клиента **30 с**.

**Ошибкой** считается ответ с кодом 4xx или 5xx, а также запрос, не получивший ответа (тайм-аут, обрыв соединения).

**Перцентили** (p50, p95, p99) вычисляются **методом ближайшего ранга**: значения сортируются и берётся значение с номером ⌈p·n/100⌉.

**Запросов в секунду** — число запросов, отправленных в окне измерения и завершившихся до его конца (в том числе с ошибкой), делённое на 60 с. `sent_rps` в JSON — частота отправки.

Параметры поиска (аэропорты, даты) и интервалы открытого режима выбираются генераторами с постоянными начальными значениями 42 и 43, поэтому все версии сервиса получают одинаковую последовательность запросов.

### Один замер вручную

Скрипт запускается внутри контейнера `search` и обращается к сервису по адресу `localhost:8000`:

```sh
docker compose exec -T search python load.py --mode closed --clients 10 --output /tmp/load.json
docker compose exec -T search python load.py --mode open --rate 5 --output /tmp/load.json
docker compose cp search:/tmp/load.json ./results/load.json
```

На экран выводятся число запросов, запросы в секунду, p50, p95, p99, максимум, доля ошибок — для поиска и для `/health`.

### Полный цикл замеров

```sh
python run_measurements.py
```

(на macOS/Linux — `python3 run_measurements.py`). Стенд должен быть запущен, база заполнена.

Скрипт выполняет:

1. **15 замеров** для таблицы 3: три версии × (C = 1, 10, 40, 80 и открытый режим 5 запросов/с). Перед каждым замером контейнер `search` пересоздаётся, чтобы очередь предыдущего замера не влияла на следующий;
2. **`py-spy dump`** версии `blocking_async` под нагрузкой C = 10 (задача 4.1, п. 3);
3. **два профиля** синхронной версии при C = 10: `py-spy record` на 60 с без `--idle` и с `--idle` (задача 3.6, п. 2). Профили снимаются отдельными прогонами, чтобы профилировщик не влиял на таблицу замеров.

Полный цикл длится около 25 минут. Файлы в `results` перезаписываются.

### Профилирование вручную

py-spy установлен в образе (`requirements.txt`). Сервису `search` выдано разрешение `SYS_PTRACE` в `docker-compose.yml`, uvicorn запущен первым процессом контейнера (PID 1). Запускать py-spy нужно от root (`-u root`), так как приложение работает от непривилегированного пользователя `appuser`.

Проверить, что PID 1 — это uvicorn:

```sh
docker compose exec -u root search py-spy dump --pid 1
```

Первая строка вывода должна содержать `uvicorn app.service:app`.

Снять профиль (в одном окне терминала), одновременно запустив нагрузку (в другом):

```sh
# окно 1: профиль за 60 секунд
docker compose exec -u root search py-spy record -o /tmp/profile.svg --pid 1 --duration 60
docker compose exec -u root search py-spy record -o /tmp/profile_idle.svg --pid 1 --duration 60 --idle

# окно 2: нагрузка
docker compose exec -T search python load.py --mode closed --clients 10 --output /tmp/load.json
```

Скопировать графики на компьютер:

```sh
docker compose cp search:/tmp/profile.svg ./profile.svg
docker compose cp search:/tmp/profile_idle.svg ./profile_idle.svg
```

SVG открывается в браузере. Каждый прямоугольник — функция, ширина — доля времени. **Без `--idle`** видно только время работы процессора, **с `--idle`** — ещё и время ожидания сети и базы.

### Оценки раздела 2

```sh
python estimate.py
```

Выводит средние времена опроса поставщиков (≈ 0,325; 0,535; 0,966 с), среднее время ответа при опросе по очереди (≈ 1,861 с) и одновременно (≈ 1,012 с), а также расчёт по закону Литтла: L = 5 × 1,861 ≈ 9,3 одновременных запроса (меньше 40 потоков пула) и 5 × 0,010 = 0,05 занятого соединения с БД.

### Почему так

- **sync.** Поставщики опрашиваются по очереди, поэтому запрос длится около 1,9 с. Обработчики `def` выполняются в пуле из 40 потоков; при C = 40 и 80 все потоки заняты поиском, и `/health` ждёт свободного потока. Пропускная способность упирается примерно в 40 потоков / 1,9 с ≈ 21 запрос/с.
- **blocking_async.** Обработчик `async def` выполняется в цикле событий — это один поток. `requests.get`, `time.sleep` и синхронная БД блокируют его, и сервис обрабатывает запросы строго по одному, включая `/health`. В `blocking_async_dump.txt` видно, что основной поток (`MainThread`) стоит в `socket.readinto` внутри `requests` → `provider_sync` → `search_sync`. Поэтому эта версия хуже синхронной: там 40 потоков ждут параллельно, здесь — один.
- **async.** Пока запрос ждёт поставщиков (`await`), цикл событий обслуживает другие запросы. База и три поставщика опрашиваются одновременно через `asyncio.gather`, поэтому время ответа определяется самым медленным поставщиком: p50 около 0,9 с вместо 1,7 с. p95 около 2 с, потому что поставщик P3 в 10 % случаев отвечает через 3 с, а ждём его не дольше 2 с.

### Профиль синхронной версии (C = 10)

| Операция внутри `search_sync` | Без `--idle` | С `--idle` |
|---|---|---|
| Опрос поставщиков с обработкой ответов | 88,26 % | 99,30 % |
| Чтение базы данных | 5,18 % | 0,23 % |
| Составление маршрутов | 6,22 % | 0,20 % |

С учётом ожидания почти всё время запроса уходит на ожидание поставщиков. Узкое место — ожидание сети, а не вычисления, поэтому переход на асинхронную модель даёт основной выигрыш.

## Docker: как настроен стенд

- **Один образ** (`Dockerfile`) для сервиса и заглушек; заглушки запускаются командой `uvicorn app.provider:app`.
- **Непривилегированный пользователь** `appuser` (правило из лабораторной работы №1).
- **uvicorn — PID 1**: команда `CMD` записана без оболочки `sh`, поэтому py-spy подключается через `--pid 1`.
- **Один рабочий процесс** (`--workers 1`, задача 3.4, п. 2).
- **Проверки готовности**: `pg_isready` для базы, запрос к `/health` средствами Python для веб-сервисов (в образе `python:3.12-slim` нет `curl`).
- **Порядок запуска**: `search` зависит от `db`, `provider1–3` с условием `service_healthy`.
- **`cap_add: SYS_PTRACE`** только у `search` — разрешение для py-spy.
- Сервис доступен на компьютере по адресу `http://localhost:18040` (внутри контейнера — порт 8000).

## Частые проблемы

| Признак | Причина | Что сделать |
|---|---|---|
| `py-spy: Permission denied` / `Operation not permitted` | Нет `SYS_PTRACE` или py-spy запущен не от root | Добавить `-u root`; пересоздать контейнер `docker compose up -d` |
| `py-spy: ... not a python process` | PID 1 — оболочка, а не uvicorn | Проверить `CMD` в `Dockerfile` и пересобрать образ (`--build`) |
| В маршрутах нет рейсов перевозчика `OWN` | База не заполнена | Выполнить `docker compose exec -T search python -m app.seed` |
| Контейнер долго в состоянии `starting` / `unhealthy` | Не проходит проверка готовности | Посмотреть журнал: `docker compose logs search` |
| `docker compose cp`: файл не найден | Неверный путь в контейнере | Указать путь, переданный py-spy в параметре `-o` или скрипту в `--output` |
| Переменная `SERVICE_VERSION` не применилась | Синтаксис `VAR=value команда` не работает в Windows | Использовать вариант для PowerShell или cmd (см. «Переключить версию сервиса») |
