# Бонусная программа магазинов

Микросервисное приложение для учёта бонусных баллов покупателей. Касса отправляет операцию в API, фоновый обработчик рассчитывает новый баланс, а сервисы уведомлений и аналитики получают результат.

## Как устроено приложение

В приложении шесть сервисов:

| Сервис | Назначение | Порт |
|---|---|---:|
| `api` | Принимает операции и отдаёт результаты и балансы | 8000 |
| `worker` | Обрабатывает операции и обновляет базу данных | — |
| `notifier` | Формирует уведомления о результатах операций | 8001 |
| `analytics` | Собирает статистику по магазинам | 8002 |
| `postgres` | Хранит счета и обработанные операции | — |
| `rabbitmq` | Передаёт сообщения между сервисами; панель управления | 15672 |

`api`, `worker`, `notifier` и `analytics` — отдельные приложения в своих папках. Сервисы передают сообщения через RabbitMQ. API и worker также используют PostgreSQL.

```text
Касса
  │
  ▼
 api ──► очередь operations ──► worker ──► PostgreSQL
                                    │
                                    ▼
                         loyalty.events (fanout)
                             ┌──────┴──────┐
                             ▼             ▼
                         notifier      analytics
```

### Обработка операции

1. Касса отправляет операцию в `POST /operations`.
2. API проверяет формат и отправляет сообщение в RabbitMQ.
3. API отвечает `202 Accepted`, не дожидаясь обработки.
4. Worker проверяет, не обрабатывалась ли операция ранее, и блокирует счёт покупателя.
5. Worker проверяет правила операции, записывает результат и обновляет баланс в одной транзакции.
6. Worker публикует результат в обменник `loyalty.events`.
7. Notifier и analytics независимо получают событие из своих очередей.

## Правила бонусной программы

| Тип | Что происходит | Обязательные поля |
|---|---|---|
| `purchase` | Начисляется 5% суммы чека; дробная часть отбрасывается | `amount` больше 0 |
| `return` | Списываются баллы, начисленные за исходную покупку | `amount` и `points` не передаются |
| `redeem` | Списывается указанное число баллов | `amount` и `points` больше 0 |

Дополнительные правила:

- `check_number` уникален среди применённых покупок. Повторная покупка с таким номером отклоняется.
- Покупка и оплата баллами могут использовать один номер чека.
- Возврат должен ссылаться на существующую покупку и быть оформлен на того же покупателя.
- Один и тот же чек нельзя вернуть дважды.
- При оплате баллами можно списать не больше 30% суммы чека и не больше текущего баланса.
- Баллы начисляются на полную сумму покупки, даже если часть чека оплачена баллами.
- Баланс может стать отрицательным, например, если покупатель потратил баллы до возврата покупки.

### Формат операции

Пример покупки:

```json
{
  "operation_id": "S12-K03-000154",
  "type": "purchase",
  "customer_id": "C1042",
  "store_id": "S12",
  "check_number": "S12-000154",
  "amount": "2490.00",
  "occurred_at": "2026-11-10T14:32:05+07:00"
}
```

Для всех типов обязательны `operation_id`, `type`, `customer_id`, `store_id`, `check_number` и `occurred_at`. `amount` передаётся для `purchase` и `redeem`, а `points` — только для `redeem`.

## Очереди и хранение данных

### RabbitMQ

| Обменник | Тип | Очередь | Получатель |
|---|---|---|---|
| `loyalty` | `direct` | `operations` | worker |
| `loyalty.events` | `fanout` | `notifier.events` | notifier |
| `loyalty.events` | `fanout` | `analytics.events` | analytics |

Все очереди долговечные (`durable`) и типа quorum. Сообщения об операциях сохраняются как persistent. Worker, notifier и analytics объявляют нужные очереди и обменники при запуске.

### PostgreSQL

Worker создаёт таблицы при старте:

- `accounts`: идентификатор покупателя и текущий баланс.
- `operations`: входные данные операции, результат, изменение баланса, причина отказа и время обработки.

В `operations` есть индексы по покупателю и времени обработки, а также по номеру чека и типу операции. Они используются при получении истории покупателя и проверке покупки или возврата.

### Что находится в папках

**`api/` — HTTP API**

- `main.py` — запуск подключений к базе и RabbitMQ, маршруты для операций, счетов и проверки состояния.
- `schemas.py` — Pydantic-модель и проверка входных полей операции.
- `tables.py` — описание таблиц PostgreSQL, которые API читает.
- `Dockerfile` — сборка и запуск API-контейнера.
- `requirements.txt` — библиотеки API и подключения к базе.
- `.dockerignore` — исключение временных файлов Python из контекста сборки.

**`worker/` — обработка операций**

- `main.py` — чтение очереди, сохранение результата и публикация событий.
- `domain.py` — модели и бизнес-правила бонусной программы; модуль не зависит от RabbitMQ и SQLAlchemy.
- `db.py` — таблицы, запросы и операции с базой данных.
- `Dockerfile` — сборка и запуск фонового обработчика.
- `requirements.txt` — библиотеки RabbitMQ и PostgreSQL.
- `.dockerignore` — исключение временных файлов Python из контекста сборки.

**`notifier/` — уведомления**

- `main.py` — получение событий, формирование текста уведомлений и HTTP-маршруты.
- `Dockerfile` — сборка и запуск сервиса уведомлений.
- `requirements.txt` — библиотеки HTTP API и RabbitMQ.
- `.dockerignore` — исключение временных файлов Python из контекста сборки.

**`analytics/` — статистика**

- `main.py` — получение событий, подсчёт показателей магазинов и HTTP-маршруты.
- `Dockerfile` — сборка и запуск сервиса аналитики.
- `requirements.txt` — библиотеки HTTP API и RabbitMQ.
- `.dockerignore` — исключение временных файлов Python из контекста сборки.

`docker-compose.yml` описывает все шесть контейнеров, их переменные окружения, порты, тома и порядок запуска. Dockerfile сервисов используют многостадийную сборку; приложения запускаются от пользователя `appuser`.

## HTTP API

### Основные маршруты

| Метод | Путь | Результат |
|---|---|---|
| `POST` | `/operations` | Отправка операции; ответ `202` содержит `operation_id` |
| `GET` | `/operations/{operation_id}` | Результат обработки или `404`, если операция ещё не обработана |
| `GET` | `/accounts/{customer_id}` | Баланс и до 20 последних операций покупателя |
| `GET` | `/health` | Состояние подключений к PostgreSQL и RabbitMQ |
| `GET` | `/notifications?customer_id=C1042` | Уведомления выбранного покупателя |
| `GET` | `/stores` | Статистика всех магазинов |
| `GET` | `/stores/{store_id}` | Статистика магазина или `404`, если событий нет |
| `GET` | `/stats` | Счётчики событий сервиса |

Некорректный формат операции приводит к ответу `422`. Если RabbitMQ не подтверждает публикацию, API отвечает `503`.

### Пример отправки покупки

После запуска приложения выполните запрос:

```bash
curl -X POST http://localhost:8000/operations \
  -H "Content-Type: application/json" \
  -d '{
    "operation_id": "S12-K03-000154",
    "type": "purchase",
    "customer_id": "C1042",
    "store_id": "S12",
    "check_number": "S12-000154",
    "amount": "2490.00",
    "occurred_at": "2026-11-10T14:32:05+07:00"
  }'
```

Ожидаемый ответ:

```json
{"operation_id":"S12-K03-000154"}
```

Для проверки результата используйте:

```text
GET http://localhost:8000/operations/S12-K03-000154
GET http://localhost:8000/accounts/C1042
```

Для чека на 2490 рублей будет начислено 124 балла: `2490 × 0.05 = 124.5`, дробная часть отбрасывается.

### Уведомления и аналитика

Notifier и analytics хранят свои данные в памяти. После перезапуска контейнера накопленные уведомления и счётчики сбрасываются.

- Уведомление содержит начисленные или списанные баллы и баланс после операции либо причину отказа.
- В `UNSUBSCRIBED` можно указать через запятую идентификаторы покупателей, которым не нужно отправлять уведомления.
- `MIN_DELAY_MS` и `MAX_DELAY_MS` задают случайную задержку, имитирующую отправку уведомления.
- Аналитика считает применённые покупки, возвраты и списания, отклонённые операции и суммы баллов.

## Настройки

Переменные можно переопределить в окружении перед запуском Docker Compose.

| Переменная | Используется в | Значение по умолчанию |
|---|---|---|
| `DATABASE_URL` | api, worker | URL PostgreSQL из `docker-compose.yml` |
| `RABBITMQ_URL` | все сервисы | URL RabbitMQ из `docker-compose.yml` |
| `POSTGRES_USER` | postgres | `loyalty` |
| `POSTGRES_PASSWORD` | postgres | `loyalty_pass` |
| `POSTGRES_DB` | postgres | `loyalty` |
| `RABBITMQ_DEFAULT_USER` | rabbitmq | `loyalty` |
| `RABBITMQ_DEFAULT_PASS` | rabbitmq | `loyalty_pass` |
| `MIN_DELAY_MS` | notifier | `200` |
| `MAX_DELAY_MS` | notifier | `1500` |
| `UNSUBSCRIBED` | notifier | пустая строка |

Указанные учётные данные предназначены для локального запуска. Для реального развёртывания задайте собственные значения.

## Запуск

Требуются Docker и Docker Compose. Выполняйте команды из папки `lab-5`.

Сборка и запуск:

```bash
docker compose up --build
```

Запуск в фоне:

```bash
docker compose up --build -d
```

Полезные команды:

```bash
docker compose ps                 # состояние контейнеров
docker compose logs -f worker     # логи worker
docker compose logs -f api        # логи API
docker compose down               # остановка; данные томов сохраняются
docker compose down -v            # остановка и удаление томов с данными
```

После запуска доступны:

- API: <http://localhost:8000>
- Notifier: <http://localhost:8001>
- Analytics: <http://localhost:8002>
- Панель RabbitMQ: <http://localhost:15672> (`loyalty` / `loyalty_pass`)

PostgreSQL и RabbitMQ запускаются первыми. Worker ждёт их готовности и создаёт таблицы; API запускается после старта worker. Notifier и analytics ждут готовности RabbitMQ.
